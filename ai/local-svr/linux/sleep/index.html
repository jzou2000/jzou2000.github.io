Control sleep/suspend Event

Is there a way to disable and enable timeout-suspend on cachyos

Gemini said

Yes, absolutely. Because CachyOS is built on top of Arch Linux, handling power management is beautifully predictable.

Depending on your window manager (KDE Plasma, GNOME, or Hyprland), your desktop environment can sometimes override general commands. The most bulletproof, global way to toggle the idle timeout-suspend is at the systemd level.

Here are the best ways to completely control this, from a rapid temporary switch to a permanent toggle.

Method 1: The Quick Systemd “Mask” (Easiest & Most Reliable)

Systemd handles your hardware’s underlying sleep triggers. If you “mask” the sleep and suspend targets, systemd will redirect any sleep requests directly to /dev/null, effectively rendering the machine incapable of falling asleep—even if a desktop environment tells it to.

To Disable Inactivity Suspend completely:

sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target

To Enable it again later:

sudo systemctl unmask sleep.target suspend.target hibernate.target hybrid-sleep.target

Why this is great for your workflow: If you have long, unsupervised ComfyUI queues running overnight, dropping the mask command guarantees the desktop won’t randomly sleep mid-render. When you’re done with heavy generation blocks for a few days, running unmask restores normal power efficiency.

Method 2: Systemd-Inhibit (Temporary “Don’t Sleep” Session)

If you don’t want to constantly run administrative sudo commands to turn sleep on and off, you can use systemd-inhibit. This command acts as an artificial block that prevents sleep only while a specific command is actively running, then automatically restores your default suspend behavior when the task finishes.

Example for your Hugo setup or a background render:

systemd-inhibit --what=idle --who="MyScript" --why="Rendering queue active" hugo --destination ./public

The system will completely block an inactivity-suspend timeout until the Hugo command completely exits. The moment it finishes, the normal idle timeout clock starts ticking down again.

Method 3: Desktop Environment Native CLI Toggles

If you prefer to toggle the actual desktop environment settings instead of blocking the underlying system hooks, you can change the configuration parameters on the fly via the terminal.

If you are running KDE Plasma (CachyOS Default):

KDE manages these profiles via powerdevil. You can control it using the qdbus utility to set the idle timeout to 0 (which means never sleep).

  • To Disable Suspend (Set idle timeout to never):

    qdbus org.kde.Solid.PowerManagement /org/kde/Solid/PowerManagement/Actions/SuspendSession setIdleTime 0

  • To Enable Suspend (Set idle timeout back to 15 minutes / 900 seconds):

    qdbus org.kde.Solid.PowerManagement /org/kde/Solid/PowerManagement/Actions/SuspendSession setIdleTime 900

If you are running Hyprland:

If you opted for the Hyprland tiling desktop configuration on CachyOS, your sleep intervals are completely managed by the hypridle daemon.

  • To Disable Suspend: Kill the background listener daemon or stop its systemd user service.

    systemctl --user stop hypridle.service

  • To Enable Suspend: Fire it right back up.

    systemctl --user start hypridle.service

You’ve correctly identified the perfect alignment for your remote access scenarios. Both Method 1 (Systemd Mask) and Method 2 (Systemd Inhibit) give you surgical control over that CachyOS desktop (kiwi.local) precisely when you are accessing it headless or in parallel with someone sitting physically at the screen.

Since you are executing this remotely over SSH, here is exactly how to lean into those two approaches to fit your wake-and-work workflow perfectly.

Scenario A: The Machine is Suspended, You Wake It up, and Log In Remotely

When you send a Wake-on-LAN (WoL) packet or physically wake the machine, it enters the GDM/KDE login splash screen. Because nobody actually signs into a local graphical session, the OS treats the computer as “Idle” and will often pull the plug and re-suspend itself within 15 minutes, right in the middle of your remote work.

To prevent this from happening automatically every time you SSH in, you can seamlessly combine Method 2 (systemd-inhibit) right into your login process.

The Elegant Fix: Inhibit Sleep Automatically on SSH Connect

You can configure your user shell on the CachyOS box to automatically drop an anchor the moment you connect over SSH, and pull it back up when you disconnect.

Add this snippet to the very bottom of your ~/.bashrc (or ~/.zshrc) file on the CachyOS desktop:

# If this is an interactive SSH session, wrap the shell in a sleep inhibitor
if [ -n "$SSH_CLIENT" ] || [ -n "$SSH_TTY" ]; then
    if ! systemctl status sleep.target | grep -q "masked"; then
        # This keeps the machine awake for exactly as long as your terminal is open
        exec systemd-inhibit --what="idle:sleep" --who="SSH Session" --why="Remote Work Active" --mode=block "$SHELL" "$@"
    fi
fi

  • How it works: When you SSH into your desktop from your ThinkPad P53s, the desktop detects the incoming connection ($SSH_TTY). Instead of launching a normal shell, it uses systemd-inhibit to lock the system’s sleep states, and nested inside that lock is your command terminal.

  • The magic part: The very second you close your laptop terminal or type exit, the process drops, the systemd lock releases instantly, and your desktop can go back to its regular energy-saving sleep settings without any manual cleanup.

Scenario B: Someone Else is Physically Using the Machine

If your son is using the machine or it’s running active desktop workloads, you don’t want to mess up their local graphical configurations, display settings, or system responsiveness.

This is where Method 1 (Systemd Mask) shines as a master override toggle. If you know you are about to kick off a massive remote background queue (like compiling a heavy ESP32 embedded project or running a script), you can completely pull the fuse out of the sleep engine.

Simply log in over SSH and run the override:

sudo systemctl mask sleep.target suspend.target

This is fully transparent to any local user sitting at the monitor. It doesn’t prompt them, throw desktop popups, or alter their framerates. It simply tells the core system kernel: “Ignore all requests to drop power states right now.”

Once your work session is finished and you want to restore standard automatic behavior, just drop the release valve:

sudo systemctl unmask sleep.target suspend.target

Using these two native systemd utilities allows you to treat your desktop like a robust, high-availability server whenever you are working on your ThinkPad, without ever causing a single glitch for anyone using the hardware locally.
