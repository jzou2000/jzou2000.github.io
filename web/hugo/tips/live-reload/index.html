Issues in Live Reload

hugo serve builds the site when the content is changed, I can see the build on the hugo console output. However the browser doesn’t show the latest content.

That is a classic, frustrating Hugo quirk. If the console says the site rebuilt but your browser is stuck in the past, it almost always comes down to one of three culprits: browser caching, a broken LiveReload WebSocket connection, or Hugo building to memory while you’re looking at old files on disk.

Here is how to track down and fix it, ordered from the easiest fix to the most technical.

1. The Hard Refresh (Rule out Cache)

Browsers love to aggressively cache static assets like CSS, JavaScript, and even HTML pages. A standard refresh sometimes isn’t enough to force the browser to grab the newly built files.

  • Windows/Linux: Press Ctrl + F5 or Ctrl + Shift + R.

  • Mac: Press Cmd + Shift + R.

  • Deep Check: Open your browser’s Developer Tools (F12), go to the Network tab, and check the Disable cache checkbox. Keep DevTools open and refresh normally.

2. LiveReload is Blocked or Disabled

Hugo uses a tiny JavaScript snippet injected into your pages to open a WebSocket connection back to the Hugo server. When the server rebuilds, it tells the browser to refresh. If this is broken, Hugo rebuilds but the browser never gets the memo.

  • Did you accidentally disable it? Make sure you aren’t running Hugo with the fast-render or livereload flags turned off. Run it cleanly:

    Bash

    hugo server

  • Check the HTML source: Open your site in the browser, right-click, and select View Page Source. Scroll to the very bottom. You should see a script tag that looks something like this:

    HTML

    <script src="/_hugo_internal/js/livereload.js" ...></script>

    If that script is missing, Hugo might not be injecting it because your theme’s layouts are missing the {{ .Hugo.Generator }} or standard template tags in the header/footer, or you are missing a proper <body> or </html> tag in your template (Hugo looks for these tags to know where to inject the script).

3. Ghost Files in the public/ Folder

If you previously ran the bare hugo command, it generated static files into a public/ folder. Sometimes, if your local server or a proxy configuration is accidentally routing requests to that physical public/ folder instead of Hugo’s dynamic in-memory server, you will only ever see the old static files.

  • The Fix: Safely delete or rename your public/ directory in your project root:

    Bash

    rm -rf public/

    Then restart hugo server. Hugo builds everything in RAM by default during development, so it doesn’t need that folder to serve your site.

4. Grouping by Hugo Configuration (Advanced)

If you are accessing your development site across a local network, running it inside a Docker container, or using a custom domain configuration in your hugo.toml, LiveReload might be trying to connect to the wrong IP address or port.

You can force Hugo to bind correctly and tell LiveReload exactly where to look by using the --bind and --baseURL flags:

Bash

hugo server --bind="0.0.0.0" --baseURL="http://localhost"

If you try a hard refresh with DevTools open and nothing changes, check your browser’s console (F12 -> Console tab). Do you see any red connection errors matching localhost:1313/livereload?

Gemini said

Ah, that narrows it down perfectly. If the HTML page itself updates but the data or files being fetched inside your JavaScript (like a fetch('/data.json') or an updated .js module) are staying old, you are dealing with aggressive sub-resource caching.

When Hugo rebuilds a file in memory, the browser doesn’t automatically know that a file requested via JavaScript has changed, so it pulls the old version right out of its internal cache.

Here are the best ways to force your JavaScript to fetch the fresh content during development:

1. The Quick Dev Fix: Cache-Busting Query Strings

The absolute easiest way to bypass the browser cache in JavaScript is to append a unique timestamp or random string to the URL of the file you are loading. This forces the browser to treat it as a brand-new request every time the script runs.

Instead of this:

JavaScript

fetch('/data/content.json')
  .then(response => response.json())

Do this during development:

JavaScript

fetch(`/data/content.json?cb=${new Date().getTime()}`)
  .then(response => response.json())

By adding ?cb=1718000000000, the browser is forced to bypass its cache and pull the fresh file directly from the Hugo server.

2. Configure Fetch Headers

If you are using fetch() to load these files, you can explicitly tell the browser’s network layer not to look at the cache at all by adding the cache: 'no-store' option.

JavaScript

fetch('/data/content.json', { cache: 'no-store' })
  .then(response => response.json())

3. Check for a PWA / Service Worker

Does your Hugo theme feature a Progressive Web App (PWA) setup or a Service Worker? Themes designed for production often ship with service workers that intercept all network requests (fetch events) and serve them from a local cache to make the site work offline. In a development environment, this will completely break your live updates.

  • How to check: Open your browser DevTools (F12), go to the Application (Chrome/Edge) or Storage (Firefox) tab, and click on Service Workers.

  • The Fix: If you see an active service worker there, check the Bypass for network checkbox. This tells the browser to ignore the service worker’s cache completely while DevTools is open.

4. Hugo Pipe Fingerprinting (For Production)

If these JavaScript-loaded files are asset files managed by Hugo (like data files inside your assets/ folder), you should use Hugo Pipes to fingerprint them. This injects a unique hash into the filename itself whenever the content changes, which solves the problem perfectly for both development and production.

HTML

{{ $data := resources.Get "data/content.json" | fingerprint }}
<script>
  // Pass the hashed URL directly into your frontend JS
  const dataUrl = "{{ $data.RelPermalink }}"; 
  fetch(dataUrl).then(...);
</script>

Which method fits best depends on how you are currently serving or generating that file. Are these files sitting in your static/ folder, or are they generated dynamically by Hugo?

Gemini said

Ah, that explains the mystery completely! The shift from your custom Node.js setup to running hugo server directly is exactly why you’re noticing this behavior now.

When you were running your own Node.js server, it likely served assets with standard development headers (like Cache-Control: no-cache or max-age=0), or it simply didn’t send aggressive caching headers at all, forcing the browser to ask the server if the file had changed on every request.

hugo server, on the other hand, is optimized to mimic a lightning-fast production environment out of the box. It intentionally tells the browser to aggressively cache files in memory so the local site feels instantaneous. Because the file is requested via JavaScript (fetch/XHR) rather than a direct page load, the browser simply grabs its cached copy without even asking Hugo if a newer version exists.

Since you want the file to be cached efficiently in production but remain perfectly responsive during development, here are the two best ways to handle it:

1. The Hugo Native Way: Cache-Busting via Resource Fingerprinting

This is the golden standard for Hugo development. Instead of forcing the browser never to cache the file, you let it cache it forever—until the content changes. When the content changes, Hugo generates a new unique hash (fingerprint) in the filename.

To do this, move your shared file from the static/ directory into your assets/ directory (e.g., assets/data/shared-content.json).

Then, in your Hugo template where you initialize your JavaScript, expose the dynamically generated URL:

HTML

{{ $sharedFile := resources.Get "data/shared-content.json" | fingerprint }}
<script>
  // Hugo will output something like: "/data/shared-content.abcd1234...json"
  const sharedFileUrl = "{{ $sharedFile.RelPermalink }}";
  
  // Your frontend script then fetches this exact URL
  fetch(sharedFileUrl)
    .then(res => res.json())
    .then(data => console.log(data));
</script>
  • Why this rules: During hugo server development, every time you modify the file, Hugo instantly calculates a new hash, the URL changes, and your JS grabs the fresh data immediately. In production, the filename remains static until you edit it, allowing browsers and CDNs to cache it aggressively.

2. The Dev-Only Environment Flag

If you prefer not to touch Hugo Pipes or move files into assets/, you can use Hugo’s environment variables to only apply a cache-busting query parameter when you are running locally.

In your template where the fetch happens:

HTML

<script>
  let url = "/data/shared-content.json";
  
  // Only append a timestamp if Hugo is running in development mode
  {{ if hugo.IsServer }}
    url += "?v=" + new Date().getTime();
  {{ end }}

  fetch(url)
    .then(res => res.json())
    .then(data => { /* ... */ });
</script>
  • Why this rules: When running hugo server, the output becomes /data/shared-content.json?v=1718000000, bypassing the cache. When you run a final hugo build for production, it drops the query string entirely, leaving you with a clean, perfectly cacheable static asset.

Using either of these keeps your production performance intact while saving you from having to manually clear your browser cache every time you make an edit locally!
